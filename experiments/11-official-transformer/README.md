# 11：同一份输入，交给官方网络代码，数值能对上吗？

首轮计算的结果很接近，但不是逐项完全相等。这个检查暂时没有发现很大的网络实现偏差；它只检查一次计算，不能据此说整个推理程序已经等价，或者代码差异一定不会影响最终抓取。

为什么做：前面的实验都使用我们当前的 Diffusers 推理程序。要研究模型为什么抓错，先要检查是不是这个程序把输入或网络计算改错了。

怎么试：使用已有同一份权重，把实验09中“原布局、拿牛奶、关闭系统提示、种子198”的真实输入数组，直接交给官方 framework 的原生网络。照片已经编码成视觉数组，文字也已经编码；此次不重新缩放照片、不重新编码、不换随机噪声。没有下载新权重，也没有改模型库。

实际得到什么：用于计算动作的16个中间向量，进入网络时与原记录逐项相同。经过全部36层后，最终中间数组的相对差异约 **0.86%**。把两份数组交给同一个官方动作输出头，得到的前10维动作更新值相对差异约 **0.33%**。

这两个百分比只表示数值差异，不是理解程度，也不是抓取成功率。这里的更新值用于逐步去除噪声，不是机械臂末端移动速度，也不是已经生成完的可执行动作。

还没有做到：两边使用不同的 PyTorch 版本和注意力计算后端，差异是否来自数值精度尚未单独验证；这里只运行第一轮去噪，没有完成30轮采样或新的 MuJoCo 执行。照片预处理、时间表及完整官方服务仍需继续对照。

官方原生网络从已下载文件加载814个参数键，全部找到且形状匹配。BF16用于主体参数，时间嵌入MLP为FP32。此运行的 PyTorch 为2.11.0+cu130、cuDNN9.24；原 Diffusers 记录来自PyTorch2.14。两侧动作头比较使用同一官方加载的权重，参考输出由原记录的中间数组重算，不是另一次直接捕获的 Diffusers head 输出。

原生生成分支有266个真实token，另附一个padding行。捕获工具最初因行数断言中止，未产生比较结果；修复时只按原生索引取回16个真实动作token，排除padding，没有修改模型计算。对应全局索引371–386，生成分支行250–265，详见结果中的 `native_layout`。这项捕获工具修复不会改变此前的策略执行实验。
