# 11：同一份输入，交给官方网络代码，数值能对上吗？

把同一份已编码输入交给官方网络代码，跑完30次计算后，两边得到的动作数值仍接近。中间数组的差异会累积，因此还不能说两套程序完全相同，更不能由此断言机械臂实际会抓谁。

这次是在查：抓错物体，会不会是我们使用的网络实现算偏了？它缩小了这个疑问的范围，尚未找出抓错的根因。照片如何缩放、如何编码，以及完整官方服务的执行结果仍需另查。

为什么做：前面的实验都使用我们当前的 Diffusers 推理程序。要研究模型为什么抓错，先要检查是不是这个程序把输入或网络计算改错了。

怎么试：使用已有同一份权重，把实验09中“原布局、拿牛奶、关闭系统提示、种子198”的真实输入数组，直接交给官方 framework 的原生网络。照片已经编码成视觉数组，文字也已经编码；此次不重新缩放照片、不重新编码、不换随机噪声。没有下载新权重，也没有改模型库。

## 第一项：先核对一次网络计算

实际得到什么：用于计算动作的16个中间向量，进入网络时与原记录逐项相同。经过全部36层后，最终中间数组的相对差异约 **0.86%**。把两份数组交给同一个官方动作输出头，得到的前10维动作更新值相对差异约 **0.33%**。

这两个百分比只表示数值差异，不是理解程度，也不是抓取成功率。这里的更新值用于逐步去除噪声，不是机械臂末端移动速度，也不是已经生成完的可执行动作。

首轮检查的限制：两边使用不同的 PyTorch 版本和注意力计算后端，差异来源尚未单独验证。下面补做了完整30次计算，但仍没有新的 MuJoCo 执行。照片预处理、时间表及完整官方服务仍需继续对照。

## 第二项：四份输入，各跑完30次，最终动作还接近吗？

我们用了两种画面：牛奶原位、牛奶移远15 cm。每种画面分别说“拿牛奶”和“拿黄油”，共四份输入。每份都从相同的初始噪声开始，让官方网络自己连续计算30次；没有把之前保存的中间答案塞回去。

**两套网络得到的最终动作数值接近，但中间数组并非完全相同。**最后一次计算的动作中间数组，相对差异已达到约4.6%–5.0%。这说明不能把首轮的0.86%当作整段计算的差异，也不能把内部变化幅度直接当作抓取意图。

这里比较的是每份初始输入生成的第一段16步动作，没有运行新的“拍照—算动作—执行—再拍照”过程。此前的视频仍是当前 Diffusers 程序的实际执行；我们没有据此声称官方网络执行后也会抓同一个东西。

### 数值怎么读

下表的XYZ数值还在模型的归一化范围里。RMSE表示两份数组的平均差异大小，**不是米、毫米、抓取概率或成功率**。

| 画面／指令 | 官方与当前程序：XYZ差异 | 夹爪数值差异 | 最后一次动作中间数组：相对差异 |
|---|---:|---:|---:|
| 牛奶原位／拿牛奶 | 0.001058 | 0.001934 | 4.63% |
| 牛奶移远／拿牛奶 | 0.001864 | 0.001568 | 4.71% |
| 牛奶原位／拿黄油 | 0.001571 | 0.001918 | 5.02% |
| 牛奶移远／拿黄油 | 0.001322 | 0.001819 | 4.68% |

同一画面中，换“牛奶／黄油”造成的XYZ差异也相近：原位场景官方为0.003615、当前程序为0.004344；移远场景分别为0.023483、0.024108。这里只用种子198，不是多个初始摆放或成功率统计。它说明两种实现都有语言引起的数值变化，没有证明按语言换抓了目标。

反归一化后，XYZ仍是传给LIBERO位置控制器的无量纲命令，并非直接以米表示的位移。没有测量末端实际轨迹前，不能把这些误差换成毫米。10维动作的整体相对差异约0.21%–0.25%，但其中还包括旋转和夹爪，不能拿这个整体百分比代替XYZ运动误差。

### 还需注意的实现差别

本次复用已有的图像编码、文字编码和历史时间表，目的是只对照网络核心；并未从原始照片重跑完整官方输入流程。官方默认时间表与当前历史时间表存在两处整数时间条件差异，本次特意保持历史时间表相同，没有测试那两处差别的行为影响。

官方网络使用PyTorch2.11和原生注意力计算，旧记录来自PyTorch2.14／Diffusers。连续采样使用同源FlowUniPC计算器，在现有CPU环境运行；旧记录在GPU运行。主体和模型输入为BF16，采样状态及更新值为FP32。

为了检查CPU／GPU是否直接把更新步骤算出了很大差别，我们把保存的同一组30次更新值交给GPU重放。最终动作RMSE均小于1e-8，四组范围为3.68e-11–6.66e-9。这个检查只固定更新值比较计算器，没有让网络根据GPU的新状态再预测下一步，因此不能据此断言剩下的差异全部来自注意力。
